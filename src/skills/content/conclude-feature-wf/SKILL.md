**Category:** Workflow skill (wf repo).

## Purpose

Finishing pass for a completed feature or fix in the wf repository, in four steps: documentation sync, commit message, commit and worktree integration, and a clean-master check. Nothing here writes new feature code — if the change itself is unfinished, finish it first.

## Step 1 — Sync help text, README, and examples

wf's user-facing docs are generated from source; edit the sources, then regenerate — never hand-edit generated output.

**Where help text is authored:**
- Command descriptions and option help: the `nest-commander` command classes in `src/commands/*.command.ts`. `src/bootstrap/help-catalog-parser.ts` parses these statically into the help catalog, so descriptions must be string literals it can evaluate.
- Command summaries and invocation examples: `COMMAND_DOCS` in `src/common/docs/command-docs.registry.ts`. New flags and new invocation patterns get an example entry here (`{ comment, command }`).

**How it reaches users:**
- Terminal help: `src/bootstrap/help-output.ts` renders `--help` from `dist/bootstrap/commands-help.catalog.json`. The catalog is regenerated by `postbuild`, so terminal help is only current after `nr build` — stale dist shows stale help.
- README: `src/bootstrap/issue-command-docs.ts` maintains the blocks between `<!-- BEGIN GENERATED COMMAND DOCS: <cmd> -->` / `<!-- END ... -->` markers in `README.md`. Regenerate with `nr sync:generated-docs` (catalog + README in one step); verify no drift with `nr generated-docs:check`.

**Checklist:**
1. Update option/description strings in the changed command classes and add or amend `COMMAND_DOCS` examples for every new flag or invocation pattern.
2. Update hand-written `README.md` prose *outside* the generated markers where the feature changes usage; never edit inside the markers.
3. Update code comments and JSDoc examples that mention the old invocation patterns (search for the old flag/command spelling across `src/` and `docs/`).
4. Inspect `src/bootstrap/help-catalog-parser.ts`, `src/bootstrap/help-output.ts`, and `src/bootstrap/issue-command-docs.ts` when the change touches help parsing, rendering, or README generation itself — a new help construct (e.g. a new example shape) usually needs support in all three.
5. Run `nr build`, then `nr generated-docs:check`; when help or docs changed, also run `nr test:manual issue-help-doc-sync.smoke`.

## Step 2 — Generate the commit description

Summarize the *nature and scope* of the staged change, not the journey: what behavior changed, for which component. Format:

```
{type}({component}): {Description beginning with an uppercase letter}
```

- `type` from the repo's history: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
- `component` is the domain component touched (e.g. `design-conformance`, `review`, `skills`), matching recent `git log --oneline` style.
- Subject line under 100 characters. No Co-Authored-By trailer in this repo.

## Step 3 — Stage, commit, and integrate worktrees

1. Remove a stale `.git/index.lock` if present, then `git add` every intended file **immediately before** committing — the CommitterAgent reads the *staged* diff, so unstaged files are silently excluded.
2. Never stage `wf.config.*` or `verification.policy.json`; check `git diff --cached --name-only` and unstage them if present.
3. Commit through wf's own CLI:
   ```bash
   wf issue:commit -m "feat(component): Describe the change"
   ```
4. **Integrate worktrees.** If the feature was built in agent or wf worktrees (`git worktree list`, `.worktrees/`): commit inside each worktree, merge or fast-forward its branch into the source branch from the main checkout, rerun the relevant tests, then `git worktree remove <path>` and delete the merged branch; finish with `git worktree prune`. A worktree with no unique commits is removed without merging.
5. `nr build` after committing TypeScript — CLI commands run from `dist/`.

## Step 4 — Leave master clean

1. `git status` on `master` must show no feature-related modifications: everything belonging to the feature is committed; leftovers are either committed as a follow-up or deliberately discarded.
2. **Ignore dirty files unrelated to the feature** — pre-existing local modifications (e.g. local config, unrelated experiments) stay untouched; list them in the wrap-up summary instead of absorbing them into the commit.
3. Final verification: `git log --oneline -3` shows the new commit on the expected branch, `git worktree list` shows only the main checkout, `nr generated-docs:check` passes, and the build is green.
