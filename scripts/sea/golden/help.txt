Usage: wf <command> [options]

Commands:
  config                  Configure agent settings
  issue:commit            Create a git commit with an AI-generated message. Use
                         -k for the ticket key, or the key is auto-detected from
                         the branch name. When -k differs from the
                         branch-embedded ticket key, warns and prompts to pick a
                         value interactively, or fails hard with both keys shown
                         when non-interactive; --dry-run only warns. Fails hard
                         if .gitignore is staged. Blank AI commit responses fail
                         fast with provider-aware diagnostics. When a code
                         review or plan artifact already exists for the ticket,
                         its summary is used to scope the commit message
                         automatically. Use --source <plan-stem|ticket-key> to
                         point at a specific review artifact; the lookup probes
                         the tracker directory first, then the custom directory,
                         and finds the artifact in any supported format
                         (json|md|yaml|yml). When no exact artifact matches, the
                         plan manifests (.sources.json) in both directories are
                         matched by ticket key, custom plan name, source name,
                         hash, or plan stem and the matched plan's review
                         artifact is used (a token matching several plans logs a
                         warning and is skipped); then the tracker and custom
                         directories are scanned for date-prefixed variants
                         (YYYY-MM-DD-<token>-review.<ext> or the running
                         repository's scoped
                         YYYY-MM-DD-<token>-<repo-basename>-review.<ext>; other
                         repositories' scoped artifacts are ignored) and the
                         newest by mtime wins on ambiguity with a warning. When
                         no fresh diff-grounded commit description exists for
                         the staged diff, one is generated inline. When running
                         from source, use yarn start issue:commit
                         --conventional.
  issue:cowsay            Smoke-test command — verifies wf is installed and
                         invocable
  issue:create            Create tickets from standardized input (file or
                         stdin); Jira live runs enforce the ADF safety gate.
                         `stages.create` is verification-only and rejects
                         provider, model, backend, or skills configuration.
                         Internal-only sections (`### Unit Test Scope`, `####
                         Dependencies`, `### Affected Repositories`, `####
                         References`) are stripped before posting; `### Risks &
                         Assumptions` is preserved. Both `--dry-run` and live
                         creates run the ADF safety analysis.
  issue:fetch             Fetch ticket description from a tracker. NB: This
                         command will override the locally generated artifact
                         with the ticket description fetched from the specified
                         tracker
  issue:generate:lookup   Lookup the original source list for a generated ticket
                         artifact hash.
  issue:generate          Generate ticket descriptions from local files,
                         repo-scoped artifacts via --repos, URLs, or ticket
                         keys. Tracker browse URLs (e.g.,
                         https://<org>.atlassian.net/browse/<KEY>) are
                         automatically detected and fetched via the tracker REST
                         API instead of scraping HTML; self-hosted instances are
                         supported when atlassian.baseUrl is configured. Local
                         .md, .json, .yaml, and .yml files that parse as tickets
                         are imported as tickets; files that are not recognized
                         as ticket-formatted content remain plain file sources.
                         Repo-scoped generation inspects prior plan artifacts
                         anywhere under ~/.wf/<repo>/**/* and correlates them by
                         keyword similarity so synthesis prompts can reuse
                         earlier implementation context. When multiple repos are
                         supplied, the synthesis prompt also compares repo
                         conventions, including linter and formatter rules, and
                         git-hook tools across checkouts. AI synthesis always
                         runs on every source to enrich and standardize the
                         output. The AI is instructed to return a structured
                         JSON object (title, type, priority, description) that
                         is validated against the ticket schema before
                         conversion to the requested output format. When agent
                         or CLI backends are used, the provider session ID is
                         threaded across oversized-source summarisation,
                         clarification, and synthesis so all calls share
                         coherent context. Generated output enforces formal
                         writing conventions (concise prose, no contractions,
                         active voice, British English) before display or save.
                         Blank AI generate-stage responses fail fast with
                         provider-aware diagnostics. Can use an agent backend
                         when stages.generate.backend is set to agent
  issue:implement         Carry out an implementation plan from a ticket-backed,
                         hashed, or custom plan artifact. Delegates the
                         generate-and-verify loop to the configured backend
                         (Anthropic Agent SDK, OpenAI Agents SDK, or Claude CLI
                         headless mode) based on stages.implement.provider and
                         stages.implement.backend. In auto model-routing mode,
                         optional stages.implement.modelRoutingThresholds can
                         send medium/high-complexity plans to the mechanical
                         model when targeted writes or plan steps exceed
                         configured limits; targeted writes are concrete
                         affectedFiles entries, not affectedFilesContext
                         entries. Use --model-routing default or --model-routing
                         mechanical to override automatic selection. Progress
                         events are streamed to the terminal so you can follow
                         task and tool activity while edits are being generated.
                         All backends emit stable task and tool progress lines
                         plus explicit file mutation logs and verification logs
                         so terminal output stays human-readable while the agent
                         works. Verification commands are expected to be
                         repo-root-relative; stale plan artifacts that still
                         embed redundant repo-selection `cd` prefixes are
                         normalized, while cross-repo directory jumps are
                         treated as setup errors. A verification step may set
                         earlyExitPattern to a valid regex; when stdout or
                         stderr matches it, wf records the check as passed and
                         terminates the command process group, while steps
                         without it run to normal completion. Set
                         stages.implement.provider and stages.implement.backend
                         in wf.config to select the backend. Use backend: agent
                         with provider anthropic or openai for the Agent SDK
                         path, or backend: cli with provider anthropic or openai
                         for the CLI headless mode (Claude CLI or Codex CLI
                         respectively). Set stages.implement.timeoutMs to
                         override the wall-clock subprocess timeout (default: 15
                         minutes) and stages.implement.inactivityTimeoutMs to
                         override the per-message inactivity timeout (default: 2
                         minutes). For the Codex CLI backend, only command
                         execution, file changes, and tool calls reset the
                         inactivity timer — plain agent-text messages do not,
                         and ten consecutive text-only messages abort the run
                         early as a stall regardless of either timeout. Set
                         stages.implement.stallThresholdForVerificationFix to
                         override how many consecutive no-write or non-improving
                         verification fix passes the Claude CLI and Codex CLI
                         backends attempt before stopping (default: 2). The
                         Claude CLI, Anthropic Agent SDK, and OpenAI Agents SDK
                         backends also end the continuation loop after 2
                         consecutive passes that write no files, touch nothing
                         git-visible, and declare nothing; an agent that finds a
                         planned file already satisfies the plan can emit a
                         `NO-CHANGE: <path>` line in its pass summary, which
                         removes that file from the unvisited set and is listed
                         as agent-declared in the file summary (declarations are
                         ignored for unplanned, glob, or actually edited files).
                         Declarations tolerate bold, quotes, backticks, a
                         trailing period, and any keyword casing, but a
                         comma-separated list or a missing colon is ignored;
                         repeating an already accepted declaration does not
                         count as progress. Plan-step verification fix prompts
                         also tell the agent to answer a step whose target is
                         already absent with a single-line proof plus
                         `NO-CHANGE: <path>` instead of re-reading files. The
                         Anthropic backend explicitly loads ~/.claude/CLAUDE.md
                         and the repository-root CLAUDE.md, warning when either
                         file is missing. The OpenAI backend loads
                         ~/.openai/AGENTS.md and the repository-root AGENTS.md
                         with the same warning behavior and only exposes an
                         exact-match verify_command tool for whitelisted
                         verification commands. When running from source, use
                         `yarn start issue:implement ...` for the implementation
                         stage and `yarn start issue:commit --conventional` to
                         stage the final conventional commit once the work is
                         accepted. Unsupported providers (google, deepseek) fail
                         fast with a clear error listing supported providers.
                         backend: standard is rejected at runtime because the
                         implement stage requires an agent-capable backend.
                         Blank AI findings responses fail fast with
                         provider-aware diagnostics instead of generic parse
                         errors. Repo conventions are detected up front and
                         threaded into every backend prompt, including
                         continuation passes, so formatter and structural ESLint
                         constraints survive context compaction. Plan complexity
                         is computed deterministically from plan size (targeted
                         writes, steps, phases, new repositories) combined with
                         the highest model-assessed risk severity; the model
                         does not estimate it. A complexity-gated commit policy
                         controls whether the backend may self-commit:
                         low-complexity plans permit a single commit; medium and
                         high plans block commits and rewind any self-made
                         commits via git reset --soft, re-staging the content so
                         issue:commit handles the final message. Enforcement
                         always runs even if the backend throws, and any git
                         safety-check failure (shallow repo, detached HEAD,
                         missing upstream) is logged and treated as a skip
                         rather than an error. Rename and removal work is
                         verified against the needle: every backend is told to
                         search it case-insensitively across the whole
                         repository (docs, specs, config, env files and CI
                         included) until zero matches remain, and the OpenAI
                         search tool skips binary files, node_modules, dist and
                         .git. Plan entries with status `to-delete` are orphaned
                         files the agent should delete; the Anthropic Agent SDK
                         backend provides a path-guarded DeleteFile tool, and a
                         deleted file counts as done in the continuation loop.
                         Run issue:fetch then issue:plan before calling this
                         command for ticket-backed workflows. When a hashed plan
                         artifact is provided, the action is inferred from the
                         filename/manifest and `--action` becomes optional, but
                         any supplied action is still validated against the
                         resolved artifact. Before implementation, the command
                         runs an interactive branch creation workflow: prompts
                         to create a new branch or stay on the current one, then
                         only checks the working tree for uncommitted changes
                         when a pull is needed. When staying on the current
                         branch, the user is asked whether to pull; stashing is
                         only triggered if a pull is accepted. When creating a
                         new branch, uncommitted changes are stashed before
                         pulling the source branch (dev or main). After each
                         pull, runs a dependency install via the detected
                         package manager (bun, pnpm, yarn, or npm); use
                         --skip-install to suppress. The install is skipped
                         automatically, with no warning, when the repo has no
                         package.json (e.g. Terraform-only repos). Failures are
                         surfaced as warnings and never abort the command.
                         Generated branch names exceeding 100 characters are
                         automatically truncated at the nearest word boundary.
                         Use --silent to auto-stash without prompting; branch
                         selection and naming still prompt when a TTY is
                         available. Use --no-branch to skip branch creation and
                         work directly on the current branch. Use
                         --branch-name-pattern to override the enforced branch
                         name validation regex from git.branchNamePattern
                         config. Branch names are validated when the branch is
                         created, against git ref conventions and the resolved
                         naming pattern (--branch-name-pattern, else
                         git.branchNamePattern, else built-in patterns). Names
                         entered at the branch prompt are trimmed, a pasted `git
                         checkout -b`/`git switch -c` prefix is stripped, and
                         input is validated inline with the specific rejection
                         reason. When branch creation still rejects a name,
                         interactive runs log the reason to the agent log and
                         reopen the branch-name prompt instead of aborting;
                         non-interactive runs fail fast. An invalid
                         --branch-name-pattern regex is rejected before any work
                         starts, and an invalid git.branchNamePattern regex
                         fails config validation at startup. When running
                         against multiple repos, repos absent from the plan's
                         affectedRepositories and newRepositories are skipped
                         with a log message. When a plan declares
                         newRepositories, those repos are scaffolded as sibling
                         directories and prepended to the execution order so
                         they run before existing repos. Plan-step verification
                         runs by default; set
                         stages.implement.planStepVerification.enabled to false
                         to turn it off, and it skips itself with a log line
                         when there are no changes, no assessed steps, a new
                         repo, or a commit policy that allows direct commits.
                         When it runs, a post-implementation AI auditor re-reads
                         the diff and scores each plan step as done,
                         partially-done, not-done, not-applicable, or
                         unverifiable. Terminal done, not-applicable, and
                         unverifiable verdicts are sticky and never reassessed;
                         only pending steps receive another fidelity pre-pass
                         and fix round. A finding that survives one targeted fix
                         round is suppressed with a WARN log and summary count.
                         Each assessor prompt renders its example response from
                         the real [Plan step N] indices being assessed and tells
                         the model never to renumber from 0; a reply with an
                         index outside the assessed set, or none of the expected
                         indices, fails the attempt (logged as
                         `step-verify.assess.attempt-failed`) and is retried
                         once instead of being filled in as not-done, while a
                         single omitted index still falls back to not-done.
                         stages.implement.planStepVerification.stallWindow
                         (default: 3) uses the pending-count window to stop a
                         remaining pending set that no longer shrinks.
                         stages.implement.planStepVerification.mode selects the
                         assessor strategy; when omitted, wf routes
                         automatically: high-complexity plans use pull,
                         low-complexity plans use push, and medium-complexity
                         plans use push when the measured diff fits the push
                         evidence budget and pull when it exceeds it; the choice
                         and its reason are logged as step-verify.mode=<mode>
                         (<reason>), and auto routing falls back to push when
                         the assessor provider is not anthropic or openai. An
                         explicit push or pull always wins. push collects git
                         diff evidence and, when verification commands ran
                         during implementation, injects a ## Command execution
                         evidence section listing their outcomes, the commit
                         policy, staged files, and commit count — allowing
                         command-execution plan steps to be assessed as done or
                         not-done rather than unverifiable; pull spawns an agent
                         with live repository access via chatTurn so the
                         assessor can read files directly, is given a host-built
                         ## Mandatory inspection checklist of every changed and
                         untracked file plus the ## Command execution evidence
                         section, and must list the files it inspected in
                         inspectedPaths; a done or not-applicable step that
                         names a checklist file missing from inspectedPaths is
                         downgraded to unverifiable
                         (step-verify.pull.coverage-gap), and an empty
                         inspectedPaths for a non-empty checklist fails the
                         attempt. A pull provider outside anthropic or openai
                         ends only the verification run (step-verify.error), not
                         the implement workflow.
                         stages.implement.planStepVerification.provider and
                         .model override the provider and model used by the
                         assessor; provider must be anthropic or openai when
                         mode is pull. When only .model is set without
                         .provider, the implement stage provider is used.
                         stages.implement.planStepVerification.backend overrides
                         the AI backend used by both the step assessor and the
                         spec-fidelity pre-pass; valid values are agent, cli,
                         and standard. When set alongside provider and model,
                         the named backend is used instead of the default
                         implement-stage backend; omit to inherit it. Push mode
                         sizes its diff evidence from the measured changeset
                         instead of fixed per-file caps: evidence up to 60k
                         characters is sent whole, and up to 240k characters
                         (including the changed-files list) is still sent whole
                         in one call. Larger changesets are assessed in phases,
                         one call per group of steps, each with the full
                         changed-files list and uncut diffs of the files its
                         steps name (logged as step-verify.assess.phased). A
                         file counts as named by a step only when its whole
                         repo-relative path appears in the step text (an
                         optional leading ./ is accepted), so a step naming
                         src/a.tsx no longer pulls in src/a.ts; this applies to
                         phased grouping, evidence prioritisation, the
                         spec-fidelity diff budget, and the pull-mode
                         coverage-gap check. Only a group that still cannot fit
                         is cut to head and tail slices with an Evidence
                         completeness section, a gap-aware unverifiable rule,
                         and WARN logs (step-verify.evidence.over-ceiling,
                         step-verify.diff.truncated, step-verify.diff.omitted,
                         step-verify.unverifiable.evidence-gap); the
                         spec-fidelity pre-pass applies the same allocation to
                         its diff with a 120k ceiling and logs
                         step-fidelity.diff.truncated.
                         step-verify.evidence.budget is always logged. Codex CLI
                         uses codex exec --output-schema with a temporary schema
                         file. Assessed and complete events include done,
                         not-applicable, partially-done, and not-done counts
                         plus unverifiable counts. The fallback is logged once
                         as `ai.model.fallback`. Before each verification round,
                         a spec-fidelity pre-pass runs one sequential AI call
                         per assessed step to detect literal claim deviations —
                         regex patterns, required parameters, exact threshold
                         values, and string literals — against the diff. The
                         fidelity pre-pass uses the same
                         planStepVerification.provider, .model, and .backend
                         overrides as the step assessor, falling back to the
                         implement-stage provider and backend when none are
                         configured. Steps with confirmed concrete mismatches
                         receive a [SPEC FIDELITY ERRORS] annotation that causes
                         the step assessor to score them partially-done and
                         enter a fix round even when the code looks
                         superficially complete. Warning-severity findings (diff
                         is silent on a claim) are surfaced but do not trigger a
                         fix round. When the plan carries a `stepIntents` entry
                         for a step, the pre-pass adds it to the prompt for that
                         step, and a literal that differs from the diff is
                         downgraded to a warning when the diff still satisfies
                         the stated intent (only intents checkable from the diff
                         count); per-repo step filtering keeps each intent with
                         its step, and plans without `stepIntents` behave as
                         before. an agent that cannot or should not implement a
                         step as written can add a final-message line
                         `PLAN-PROBLEM: <step number from the Plan steps list> |
                         <reason> | <what you did instead>` (exactly three
                         non-empty parts; bold, bullet, backticks, `Step N` and
                         any casing are tolerated; out-of-range steps and
                         malformed lines are ignored with a WARN log; the first
                         report per step wins; text is capped at 500 characters
                         and 20 reports per run). Reports are accepted on every
                         backend (Codex reads only its final message), printed
                         as `Plan problem reported for step N`, saved as
                         run.planProblems in the newest implement-verification
                         run file, shown to the spec-fidelity auditor and to the
                         fix-round prompts, and listed in the review context;
                         under `wf issue` with a saved session, plan problems
                         and blocking spec-fidelity deviations are also stored
                         per repo in the `records` of the implement stage in the
                         session file (deduplicated, at most 20 per repo, 500
                         characters each) and passed to the review stage as a
                         labelled data block in its prior-stage context; the
                         auditor still judges whether the alternative is sound,
                         and verification commands remain the hard gate. Only
                         the spec-fidelity pre-pass reads intents; the step
                         assessor sees step text alone. The pre-pass is skipped
                         when the diff is empty and never throws; any internal
                         error is silently swallowed so the verification loop is
                         unaffected. Ordinary review-stage chat requests remain
                         unstructured unless they explicitly provide a response
                         schema, so they do not inherit the review schema
                         accidentally. Runs a Figma implementation pass when
                         stages.implement.figma is true or --figma is passed;
                         Figma frame links stored in the plan manifest by
                         issue:plan are re-read at implement time to fetch
                         design context via the Figma REST API, injecting frame
                         name, dimensions, and screenshot URL into the backend
                         prompt so the implementer can reconcile generated code
                         against spacing, colour, and component-structure
                         constraints before committing. The manifest is resolved
                         directly from the ticket artifact path so the correct
                         links are always loaded without a branch-name search.
                         Figma frame URLs that lack a `?node-id=` query
                         parameter are skipped with a WARN rather than
                         generating a malformed API call. If all frame fetches
                         fail despite valid links being present, a WARN is
                         written to the on-disk agent log to distinguish network
                         or token failures from the links-absent case.When the
                         plan artifact lists uiDesignScreenshots (set by
                         issue:plan --ui-design-screenshots), the Anthropic
                         agent backend adds their paths to the task brief and
                         grants the sandbox read access to each parent directory
                         (logged), and the Claude CLI backend passes each parent
                         directory with --add-dir and repeats a one-line
                         reminder on continuation passes; the OpenAI agent
                         backend cannot show images and logs a warning. The
                         design conformance check is off by default; it runs
                         when stages.implement.designConformance.enabled is
                         true, or automatically when wf issue is started with
                         --ui-design-screenshots, which switches the check on
                         even when enabled is false and merges it with the rest
                         of stages.implement.designConformance (maxScreenshots,
                         provider, model, backend). Without the flag the config
                         alone decides: enabled true runs the check and enabled
                         false or unset does not. The flag only requests the
                         check; the screenshots still come from the plan
                         artifact, so a run started past the plan stage against
                         a plan stored without them reports that the check was
                         skipped. It adds an advisory check after verification:
                         one sequential AI call per screenshot (capped by
                         designConformance.maxScreenshots) compares the
                         implement diff against that image, and any deviations
                         are printed under Design conformance (advisory), logged
                         as design-check, and saved as run.designConformance in
                         the newest implement-verification run file. The check
                         never fails the run. Its target follows the same
                         override rules as planStepVerification:
                         designConformance.provider, .model and .backend
                         override the implement stage target, and each one that
                         is unset falls back to stages.implement (.model alone
                         uses the implement stage provider; .provider requires
                         .model). The backend selects how the call runs.
                         standard sends the screenshot as an inline image
                         through the provider API (anthropic or openai). cli
                         runs the Claude CLI (anthropic) or Codex CLI (openai)
                         with the screenshot path in the prompt, and agent runs
                         the Anthropic Agent SDK with the screenshot directory
                         readable; the OpenAI agent backend cannot read images,
                         so it is skipped with a warning, as is any provider
                         other than anthropic or openai. designConformance
                         accepts only enabled, maxScreenshots, provider, model,
                         and backend.
  issue:plan              Plan ticket implementation from a local artifact or
                         repo-scoped custom artifact. If a local artifact is not
                         found, the command will attempt to fetch it from the
                         primary tracker. Use --force to fetch and recreate
                         artifacts. Repo-scoped planning inspects prior plan
                         artifacts anywhere under ~/.wf/<repo>/**/* and
                         correlates them by keyword similarity so planning
                         prompts can reuse earlier implementation context.
                         Planning prompts include detected repository test
                         conventions and ecosystem-specific verification
                         guidance so generated steps match local test patterns
                         and only reference allowed command forms. Node
                         verification commands use the detected package manager:
                         npm uses `npm run <script> -- <args>`, yarn uses `yarn
                         <script> <args>`, pnpm uses `pnpm run <script> <args>`,
                         and bun uses `bun run <script> <args>`; the same syntax
                         is used by validation and retry guidance. When a design
                         system is detected, observed element class conventions
                         (e.g. h1–h6 heading classes, grid-gap token choices,
                         responsive grid-cols breakpoint tiers mined from real
                         .vue/.tsx files) are included in the plan prompt; the
                         design-system block is omitted for non-UI tickets so
                         the prompt stays focused. Existing components and
                         composables whose names share significant vocabulary
                         with the ticket are surfaced in the plan prompt as
                         reuse candidates so the planner can reference them
                         before creating new files; repos that place UI files
                         outside `app/components` or `app/composables` receive
                         no candidates. Generated plans are semantically
                         validated before they are saved: wf retries once with
                         explicit repair feedback when a draft omits rename
                         targets, uses a non-allowlisted verification command,
                         or contradicts detected test conventions. Steps that
                         delete, drop, remove, replace or rename a term also
                         need a case-insensitive zero-match verification command
                         such as `bash -c '! git grep -I -i -q -F <term>'` (or a
                         `needle-search-required` waiver); a missing or
                         `\\b`-only check is reported as an advisory quality
                         risk after the repair retry. A step that writes a spec
                         with a mocked collaborator must also state that the
                         collaborator is asserted called after the act step (or
                         carry a `test-call-assertion-required` waiver); this is
                         reported the same advisory way. A plan may carry an
                         optional `stepIntents` array, index-aligned with
                         `steps` (same length, `null` for steps without an
                         intent): the planner is told to emit an intent only for
                         steps that prescribe a literal (a call chain,
                         signature, regex or test name), phrased as a goal
                         checkable from the diff; a length mismatch fails plan
                         validation, and markdown artifacts store each intent as
                         an `Intent:` line directly under its numbered step. The
                         planner is told to search the needle case-insensitively
                         across the whole repository, including docs, specs,
                         config, env files and CI, and may mark orphaned files
                         it deletes with the `to-delete` file status (rejected
                         in affectedFilesContext). A step that names two config
                         keys (backticked or quoted, starting with `ai.`,
                         `stages.`, `git.` or `figma.`) with the same final
                         segment, or that adds a `resolve*`, `get*`, `pick*`,
                         `select*` or `build*` function, is checked against the
                         repository with `git grep`; when an existing resolver
                         in a file the plan does not list already reads those
                         keys or defines that name, the plan records a
                         `duplicate-resolver` risk ("reuse <name> in
                         <file>:<line>, or state why it cannot be reused")
                         without a repair retry. The lookup is skipped when no
                         repository directory is known and fails open on any git
                         error. Targeted verification commands are interpreted
                         as repo-root-relative: redundant `cd <repo>` prefixes
                         are normalized away, while commands that change
                         directories outside the selected repository are
                         rejected. When `--figma` is passed or
                         `stages.plan.figma` is `true`, Figma frame links found
                         in the ticket description or acceptance criteria are
                         extracted with their full query strings (including
                         `?node-id=` parameters) and stored in the plan
                         manifest, enabling Figma REST API design context
                         injection during a later `issue:implement --figma` run
                         and `issue:review --figma` run. When no inline Figma
                         links are found but a design system is detected in the
                         repo, an interactive prompt asks for frame links in TTY
                         sessions; links supplied this way are stored in the
                         manifest but are not threaded into the AI generation
                         context.
  issue:pr                Create a pull request from a plan artifact
                         (auto-detects ticket from branch).
  issue:review            AI-powered code review of local changes,
                         ticket-associated pull requests, or PR diffs. Each
                         review includes nested trace provenance, issue-local
                         suggestions, and diff-aligned inline comment anchors.
                         Ticket-keyed reviews are cached to
                         `<ticket>-review.<format>`, where the format comes from
                         `-f/--format` or `stages.review.outputFormat` (default
                         md); a cached artifact is served regardless of the
                         format it was written in, and regenerating with
                         `--force` under a different format replaces the stale
                         variant so each ticket keeps exactly one review
                         artifact. In multi-repo runs the artifact gains a
                         repo-scope suffix —
                         `<ticket>-<repo-basename>-review.<ext>`, one file per
                         repository — so each repo's cached result is stored
                         independently and the first repository's cached review
                         is never served to subsequent repositories in the same
                         run; mono-repo runs stay unscoped so the artifact
                         shares its stem with the commit-description sidecar.
                         The review rubric includes Accessibility (roles, focus
                         states, screen-reader operability), Scope & necessity
                         (replaces the former separate Scope and Necessity
                         criteria), and Pattern grounding (checks flagged
                         patterns against actual codebase conventions before
                         raising an issue) among its default criteria. The
                         verdict follows severity: a review that contains any
                         `error` issue is recorded as Changes requested even
                         when the model returned `approved: true`, while warning
                         and info issues do not block approval. Reviews are
                         enriched with detected repo conventions (linter,
                         formatter, language, TypeScript config) and structured
                         verification results; for eligible PR and
                         single-repository reviews, lint, typecheck, and test
                         run live in an invocation-scoped disposable git
                         worktree after the exact reviewed diff is applied,
                         leaving the target repository untouched. Verification
                         records passed, failed, or not-run status and are
                         persisted beside the review in Markdown, JSON, and YAML
                         output. Use `--skip-verification` to bypass it. Blank
                         or blocked AI review responses fail fast with
                         provider-aware diagnostics instead of generic parse
                         errors; Codex CLI schema/configuration rejections
                         preserve the provider detail and are not reported as
                         rate-limit failures. Runs the SonarQube CLI (`sonar
                         analyze secrets` then `sonar analyze`) when
                         `stages.review.sonar` is `true` or `--sonar` is passed;
                         requires `sonar` on PATH and an authenticated `sonar
                         auth status`. Scopes the scan to staged changes when
                         present, otherwise to the merge-base diff against a
                         source branch recovered from `--session-id`, a
                         locally-persisted session for `--ticket-key`, a plan
                         manifest, git reflog, or an interactive prompt, in that
                         order. A bare `--ticket-key` with no matching local
                         session, or any run where no base branch can be
                         resolved, falls back to an unscoped `sonar analyze` and
                         logs a WARN entry to the on-disk log with context
                         `sonar-stage`; a recorded source-branch lookup that
                         fails (for example an unreadable session directory)
                         logs a WARN with the same context and the scan falls
                         back to the development or upstream branch. Findings
                         are reported and logged at WARN with context
                         `sonar-scanner`, and review continues; a clean scan is
                         confirmed too, both on the console and in the persisted
                         log (at INFO), so it stays distinguishable from a scan
                         that never ran; a missing CLI or auth/project
                         misconfiguration continues the review without Sonar
                         findings, leaving other targets in the same run
                         unaffected. That failure warning is always logged at
                         WARN with context `sonar-stage` and is not hidden by
                         `--silent`. Use `--sonar-only` to run only the
                         SonarQube scan for local repositories; it skips AI
                         review, verification, Figma, comments, and chat, prints
                         findings directly, exits 0 for clean or finding-bearing
                         scans, and propagates scan/setup failures through the
                         normal error handler. CLI-backed review sessions send a
                         final human-readable epilogue after parsing the JSON
                         review; Claude CLI forks that epilogue session, while
                         Codex CLI resumes the same session because its JSON
                         exec path has no fork flag. Runs a Figma
                         design-conformance check when `stages.review.figma` is
                         `true` or `--figma` is passed; Figma frame links
                         captured from the ticket description during
                         `issue:plan` are stored in the plan manifest and
                         re-read at review time to fetch design context via the
                         Figma REST API, injecting frame name, dimensions, and
                         screenshot URL into the review prompt so the reviewer
                         model can evaluate visual conformance against the
                         original frames. If all frame fetches fail despite
                         valid links being present, a WARN is written to the
                         on-disk agent log to distinguish network or token
                         failures from the links-absent case. When
                         `--ui-design-screenshots` was passed to `issue:plan` or
                         `issue`, the resolved screenshot paths are stored in
                         the plan artifact; at review time those paths are
                         re-read and handed to the reviewer — base64-encoded as
                         multimodal prompt content for API-backed providers, or
                         as filesystem paths appended to the prompt (with each
                         screenshot directory granted via `--add-dir`) for the
                         Claude CLI backend — so the reviewer can check UI
                         conformance against the original design files. When the
                         review diff exceeds the summarisation threshold
                         (default 80 000 chars), oversized per-file patches are
                         batched into as few CLI calls as possible — grouping
                         files within a 60 000-character chunk budget — rather
                         than one call per file; each batch call returns `===
                         FILE: <path> ===`-delimited summaries and paths are
                         normalised on both sides to avoid OS separator
                         mismatches. Configure `stages.review.maxDiffLength`
                         (integer ≥ 1) to override the 80 000-character
                         threshold and `stages.review.epilogueTimeoutMs`
                         (integer ≥ 0, default 30 000 ms) to adjust the CLI
                         epilogue spawn timeout. Epilogue failures from
                         `is_error` responses or spawn errors are surfaced in
                         the console log with the first line of the extracted
                         diagnostic so the root cause is visible without opening
                         a log file.
  issue                   Complete workflow: fetch, plan, implement, review, and
                         commit. Use --from and --to to control stage range.
                         Pass --repos to specify repositories: the first repo
                         anchors artifact storage; remaining repos expand
                         execution context. Resuming from `--from implement` can
                         accept a hashed plan token or a hashed plan filename;
                         if `--action` is provided, it is validated against the
                         resolved artifact. When `--session-id` is provided, the
                         command resumes saved workflow metadata and rejects a
                         redundant positional plan token.
